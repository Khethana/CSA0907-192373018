## 1. Forms of Polymorphism in Java

Polymorphism ("many forms") allows entities to behave differently based on their context or runtime type:

### 1.1 Compile-Time Polymorphism (Static Binding / Method Overloading)
- **Definition:** Multiple methods within the same class share the same identifier but have distinct parameter lists (different number of arguments or different types).
- **Binding Mechanism:** The Java compiler (`javac`) inspects the static types of arguments passed at the call site and binds the call directly to the target method signature in the generated bytecode (`invokevirtual` or `invokestatic`).
- **Example in System:**
  ```java
  public double calculateFee(Vehicle v, int minutes);
  public double calculateFee(Vehicle v, LocalTime in, LocalTime out);
  ```
  If caller executes `calculateFee(v, 130)`, the compiler binds overload #1. If caller executes `calculateFee(v, t1, t2)`, the compiler binds overload #2.

### 1.2 Runtime Polymorphism (Dynamic Binding / Dynamic Method Dispatch)
- **Definition:** A superclass reference variable invokes an overridden method, and the specific version executed is determined at runtime based on the actual object instance on the JVM Heap.
- **Upcasting Mechanism:**
  ```java
  Vehicle[] parked = { new TwoWheeler("TN01A1"), new Car("TN02B2"), new ElectricCar("TN03C3") };
  ```
  All specialized objects are upcast to the common supertype reference `Vehicle`.
- **Dynamic Dispatch Resolution:**
  When `v.calculateFee(130)` executes:
  1. The declared type is `Vehicle`.
  2. The JVM checks the Virtual Method Table (**vtable**) of the actual object in memory (`TwoWheeler`, `Car`, or `ElectricCar`).
  3. The vtable points directly to the subclass implementation of `ratePerHour()`.
  4. Fee computes cleanly without a single `if` or `switch` branch.

## 2. Dynamic Method Dispatch Trace

### Step-by-Step Execution Trace for `parked[2].calculateFee(130)`:
1. **Declared Reference Type:** `Vehicle v = parked[2];`
2. **Actual Heap Object Type:** `ElectricCar` (instance located at heap address `0x...`)
3. **Bytecode Invocation:** `invokevirtual Task08/Vehicle.calculateFee:(I)D`
4. **Method Resolution:**
   - The JVM inspects the object header of `parked[2]` to find its class pointer (`Klass*` in Metaspace).
   - Locates `calculateFee(int)` in `Vehicle.class`.
   - `calculateFee` invokes `this.ratePerHour()`.
   - The `this` pointer holds the `ElectricCar` instance.
   - The JVM vtable for `ElectricCar` points to `Car.ratePerHour()`, which returns `30.0`.
   - Integer ceiling arithmetic computes: $\text{hours} = (130 + 59) / 60 = 3$.
   - Returns $3 \times 30.0 = \text{Rs. } 90.0$.
5. **Interface Check:**
   - The driver checks: `if (v instanceof Chargeable c) fee += c.chargingFee(10);`
   - Since `ElectricCar implements Chargeable`, it enters the block and executes `c.chargingFee(10)`, adding $10 \times 12.0 = \text{Rs. } 120.0$.
   - Final Fee = $90.0 + 120.0 = \text{Rs. } 210.0$.

## 3. Analysis of Equality Evaluation: `Car` vs. `ElectricCar`

In `FeeDemo.java`, the program executes:
```java
System.out.println(new Car("TN02B2").equals(new ElectricCar("TN02B2")));
```
**Output:** `true`

### 3.1 Why It Evaluates to `true`:
The `equals(Object o)` method in `Vehicle` is defined as:
```java
@Override 
public boolean equals(Object o) {
    return o instanceof Vehicle && regNo.equals(((Vehicle) o).regNo);
}
```
1. The left operand is `new Car("TN02B2")`.
2. The argument passed is `new ElectricCar("TN02B2")`.
3. `ElectricCar` inherits from `Car`, which inherits from `Vehicle`. Thus, `o instanceof Vehicle` evaluates to **`true`**.
4. Both instances hold `regNo = "TN02B2"`. Thus, `regNo.equals(...)` evaluates to **`true`**.
5. The method returns `true`.

### 3.2 Is This the Correct Behaviour for the Parking System?
**Yes, in the domain of physical parking facilities, this is strictly the correct behaviour.**
- **Physical Domain Reality:** A motor vehicle registration number (license plate) is a state-issued, globally unique identifier assigned to one physical automobile chassis. It is physically impossible for a standard gasoline `Car` and an `ElectricCar` with the identical registration number to exist as two separate legitimate automobiles in the campus garage at the same time.
- **Detection of Inconsistency / Fraud:** If an attendant creates a `Car("TN02B2")` record and another gate creates an `ElectricCar("TN02B2")` record, treating them as equal immediately alerts the system to duplicate entry, plate spoofing, or re-categorization of the same vehicle.
- **Liskov Substitution Principle (LSP):** An `ElectricCar` is-a `Car` is-a `Vehicle`. Substituting an `ElectricCar` where a `Vehicle` equality comparison is expected satisfies LSP.
- **Alternative (Strict Class Equality):** If the system instead used `o != null && o.getClass() == this.getClass()`, the comparison would return `false`. However, this would allow duplicate license plates to simultaneously occupy slots under different subclass types, violating the physical invariant of the campus parking facility.

## 4. Alternative Concept and Complexity Analysis

### 4.1 Dynamic Method Dispatch vs. Procedural `instanceof` Chains

#### Procedural Implementation:
```java
double fee = 0;
int hours = (minutes + 59) / 60;
if (v instanceof TwoWheeler) {
    fee = hours * 10.0;
} else if (v instanceof ElectricCar) {
    fee = hours * 30.0;
} else if (v instanceof Car) {
    fee = hours * 30.0;
} else {
    throw new IllegalArgumentException("Unknown type");
}
```

#### Comparison Analysis:

| Architectural Metric | Dynamic Method Dispatch (Task 8 Code) | Procedural `instanceof` and Casting |
| :--- | :--- | :--- |
| **Time Complexity per Call** | $\mathcal{O}(1)$ deterministic constant time. Indexed offset in vtable. | $\mathcal{O}(k)$ where $k$ is the number of vehicle types. Must execute up to $k$ sequential conditional branch instructions. |
| **CPU Branch Prediction Impact** | High efficiency. JIT C2 compiler uses bimorphic/megamorphic inlining caches. | High penalty. Sequential `if-else` causes frequent CPU branch mispredictions in heterogeneous vehicle traffic. |
| **Adding Vehicle Type $k+1$** | **Zero lines modified in existing classes.** Create new class extending `Vehicle`. | **Modifies every `instanceof` block across the system.** If an attendant adds an `EBike`, developer must hunt down every `instanceof` chain. |
| **Type Safety & Bug Resistance** | Compiler-enforced. Subclass cannot compile without implementing abstract methods. | Fragile. Developer might forget to check a subtype or order checks incorrectly (e.g. checking `Car` before `ElectricCar` would hijack the EV check!). |
